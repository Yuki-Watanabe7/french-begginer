# Development Workflow

## Issue 駆動開発ルール

1. **1 Issue = 1 目的** — 1つのIssueに複数の目的を混ぜない
2. **使用感に関わる変更はスマホで確認** — UI・UX・レイアウトに影響する変更は必ずスマホ実機で確認してからPR化する
3. **CI を緑にしてから PR 化** — ruff / pytest / npm lint / npm build が全て通ってからPRを作成する
4. **新機能追加時は Docs 更新要否を確認** — API追加・起動方法変更・CI変更を伴う場合はドキュメントも更新する
5. **Claude Code への依頼時は対象範囲・非対象範囲・完了条件を明記** — 曖昧な依頼は意図しない変更を招く

---

## GitHub Issues ベース開発の方針

- **1 Issue = 1 PR** を基本とする
- Issue には「目的」「完了条件」「スコープ外」を明記する
- 大きな機能は複数Issueに分割し、依存関係をリンクで示す
- `main` ブランチは常に動く状態を保つ
- 完了条件を満たした Issue は、既定ブランチ `main` 向けの PR 本文に `Closes #番号` を記載し、マージ時に自動で閉じる。これはマージ前に Issue を閉じないルールと両立するため、手動クローズを別手順として追加しない。マージ後にも完了条件の確認が残る場合は `Refs #番号` とし、残作業を明記する。

### Issueラベル

| ラベル | 用途 |
|--------|------|
| `feature` | 新機能 |
| `bug` | 不具合修正 |
| `chore` | 環境・設定・依存関係 |
| `docs` | ドキュメント |
| `ux` | UI/UX改善 |

## Claude Code への依頼基準

### 依頼前に書くこと

```
## 目的
（何を実現したいか）

## 背景・制約
（なぜ今必要か、守るべき方針）

## 完了条件
（何をもって完了とするか）

## スコープ外
（今回やらないこと）
```

### 依頼時の注意

- **1回の依頼で1つの関心事** に絞る（複数機能を同時に頼まない）
- エージェントは実装前に `bash scripts/ensure_branch_includes_main.sh` を通し、`origin/main` からブランチを切る。起動済みの checkout は `main` より古いことがある
- 設計判断が必要な場合は先に「方針確認」として相談する
- 生成コードは必ずレビューしてからコミット

## スマホ実機で使用感を確認する流れ

### GitHub Codespaces の場合

1. GitHub リポジトリページで **Code → Codespaces → Create codespace on main** をクリック
2. ターミナルで `docker compose up` を実行
3. 「ポート」タブで `5173` が表示されることを確認
4. `5173` の行を右クリックし **Visibility → Public** に変更
5. 表示された URL（`https://<codespace-name>-5173.app.github.dev` 形式）をスマホブラウザで開く
6. 以下の学習ループが正常に動くことを確認する:
   - 問題（動詞・時制・主語）が表示される
   - 活用形を入力して送信できる
   - 正誤フィードバックが表示される
   - 次の問題に進める

### ローカルの場合（同一WiFi）

1. `docker compose up` を実行
2. `ipconfig getifaddr en0`（Mac）でローカルIPを確認
3. スマホで `http://<ローカルIP>:5173` にアクセス

### 確認ポイント

- [ ] 文字が小さすぎないか
- [ ] 入力欄タップ時にキーボードが問題なく上がるか
- [ ] 判定ボタンが親指で押しやすい位置にあるか
- [ ] 正誤フィードバックが一目で分かるか
- [ ] 次の問題への流れがスムーズか

## PR 作成時に確認すべき項目

- [ ] CIが全て通っている（ruff / pytest / npm lint / npm build）
- [ ] `docker compose up` で起動できる
- [ ] スマホブラウザで動作確認済み（Codespacesまたはローカル）※UI変更がある場合
- [ ] 新規APIがある場合、`docs/architecture.md` の API 表を更新した
- [ ] 不要なデバッグコード・console.log を削除した
- [ ] PRの説明に「何を・なぜ・どう確認したか」を書いた

### Test plan のチェック運用

PR 本文の Test plan は、レビュアーが後から手で潰すリストではない。
**作成時点で確認済みの項目は `[x]` にする。**

| 確認手段 | Test plan の扱い |
|----------|------------------|
| `quality-check.sh` / pytest / lint など自動で通した | `[x]`。可能ならテスト名を括弧書きする |
| エージェントが curl / TestClient 等で再現して通した | `[x]` |
| スマホ実機の使用感など、人が見ないと分からない項目 | `[ ]` のまま残し、誰が確認するかを本文に書く |

人手確認が不要な項目を、過去 PR の体裁に合わせて未チェックのまま残さない。
エージェントが PR を書く場合も同じルールに従う（`CLAUDE.md` の「PR の Test plan」）。
